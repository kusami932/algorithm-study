Asymptotic Notation & Input Constraints

이 코드는 O(n^2)인가
	=> 입력 크기 N이 이 정도라면 애초에 어떤 시간복잡도의 알고리즘까지 허용되는가?
	
	Big-O와 Big-Theta는 정확히 무엇이 다른가?
	O(n)이라고 말할 때 왜 상수를 무시하는가
	왜 3n^2 + 100n + 500을 O(n^2)이라고 하는가
	Big-O의 수학적인 정의
	N = 1000과 N = 100000은 알고리즘 선택에 어떤 차이를 만드는가
	1초에 10^8번 정도 연산 가능하다 => 어떻게 사용해야 하는가
	문제의 입력 제한만 보고 O(n^2), O(n log n), O(n) 중 어떤 풀이를 노려야 하는지 판단
	같은 문제를 O(n^2)에서 O(n)으로 개선하는 사고방식 설명
	
		** 코드부터 쓰기 전에 먼저 입력 제한 N을 확인한다
	
입력 제한을 봐야 되는 이유

	정수 N개가 주어졌을 때, 두 수를 골라 합이 target이 되는 쌍이 존재하는 판단하라
		가장 자연스러운 방법: 모든 쌍을 확인하는 것 (for-for, a[i] + a[j] == target)
			ㄴ 복잡도는 O(n^2)이지만 좋은 풀이인지 나쁜 풀이인지는 N의 범위를 봐야됨
	
			N <= 1000, 1000^2 = 1,000,000 (약 100만번) => 충분히 빠름
			N <=100000 = 10^10 (약 100억번) => 일반적인 환경에선 사실상 불가능
			
				문제를 읽고 N = 100000을 보는 순간,
					=> 모든 쌍을 검사하는 O(n^2) 방법은 아닐 가능성이 높다
						ㄴ> 입력 제한 감각

점근 분석 (Asymptotic Analysis)
	특정 컴퓨터의 초 단위를 분석하는 대신
	"입력 크기가 커질 때 연산량이 어떤 비율로 증가하는가?"

	Big-O: 함수의 증가율에 대한 asymptotic upper bound
		f(n) = 3n +10일 때 f(n) = O(n)
			Big-O의 정의: 3n + 10 <= cn을 만족하는 c와 n
				n >= 10이면 3n + 10 <= 4n (c = 4, n = 10)
				3n + 10 <= 4n for all n >= 10
	
	Big-O에서 n이 중요한 이유
		점근 분석은 작은 입력에서 무슨 일이 일어나는지는 중요하지 않음
		충분히 큰 n 이후의 성장 패턴을 분석 => n >= n0
		가장 유용한 상한을 사용
		
		점근적 상한: 최소한 이것보다 빠르게 증가하지는 않음
			=> 충분히 큰 입력에서 어떤 상수배의 g(n)보다 커지지 않는다
			
		Big-Omega: 점근적 하한 (충분히 큰 n에서 f(n) >= cg(n))
		Big-Theta: 상한과 하한이 동시에 맞을 때 사용
			f(n) = Theta (g(n))
				= O(g(n))
				= Omega(g(n))
		
		f(n)과 g(n)의 증가율이 같은 차수이다
		
		f(n) = Theta(g(n)) if there exist positive constraints c1, c2, n0
		s.t. 0 < c1g(n) <= f(n) <= c2g(n) for all n >= n0
			f(n)이 위와 아래 양쪽에서 g(n)의 상수배에 끼어 있다
			
			f(n) = 3n + 10일 때, 충분히 큰 n에서
				3n <= 3n + 10 <= 4n
					ㄴ> 3n + 10 = Theta (n)
	
		실제 연산량이 정확히 선형이라면 Theta (n)이라고 말하는 것이 더 정확
			CS 이론 문제에서는 O, Omega, Theta의 차이를 구별
		
		Dominant Term: 복잡도를 단순화할 때 가장 빠르게 증가하는 항 (최고차항)만 
		상수 무시: 상수의 크기와 관계 없이 증가 패턴은 일정
			ㄴ> 실제 프로그래밍에서는 완전히 무의미하지는 않음
			
			2^n: subset enumeration 같은 알고리즘은 보통 N ~ 20 정도가 중요한 경계
			n!은 더 빠름 => 모든 순열을 검사하는 알고리즘은 N이 매우 작을때만 가능
				ㄴ> N < 8, N < 10 같은 제한을 보면 "순열 완전탐색"을 생각해볼 수 있음

코딩 테스트 문제의 1 < N < 100000은 단순한 데이터 설명이 아님
	입력 제한을 보면 허용되는 알고리즘을 역으로 추론할 수 있음
	
		N < 10: O(n!), O(2^n) | N < 20: O(2^n)
		N < 100: O(n ^ 3) | N < 1000: O(n^2)
		
		N < 10000 => O(n^2)은 위험, O (n log n) 선호
		N < 100,000 => O (n log n), O(n)
		N < 1,000,000 => O (n), 때에 따라 O (n log n)
		N  < 10^7 => 거의 O(n), O(n log n), 혹은 수학적 해결
		
		1초 10^8번이라는 기준
			C++은 1초에 약 10^8번 정도의 단순 연산을 할 수 있다고 생각하라
				실전에서는 보수적으로 10 ^ 7 ~ 10 ^ 8 정도의 단순 연산
				** Python은 C++보다 반복문 기반 연산 처리량이 훨씬 낮음
				
		왜 10^8은 절대적인 기준이 아닌가
			x++;
			unordered_map<string, vector<int>>
			를 이용한 복잡한 해시/메모리 작업은 비용이 전혀 다름
			
			같은 "한 번"이라고 세더라도 실제 CPU 명령어 수가 다름
			ㄴ> 10 ^ 8은 복잡도를 빠르게 걸러내기 위한 rough estimate
			
	
	1. 최대 N을 찾는다 (1 < N < 100,000)
	2. 생각 중인 알고리즘의 복잡도를 계산한다 (중첩 반복문이면 O(n^2))
	3. 최대 입력에서 실제 규모를 계산한다 (100,000 ^ 2 = 10^10)
	4. 현실적인지 판단한다 (10 ^ 10은 대체로 불가능)
	5. 더 나은 자료구조나 알고리즘을 찾는다 (hash set, sorting, binary search, etc)

복잡도별 입력 크기 감각
	O(1) - 입력 크기와 무관 일정한 작업만 수행 (return n * (n + 1) / 2 => N이 커도 가능)
	O(log n) - binary search 
		N = 10 ^ 9여도 log(2) 10^9 = 30번 정도만 탐색한다 (입력 크기가 커도 가능)
	O(n) - 배열 전체 한 번 흝기 
		N = 10^6 정도 자연스러움, N = 10 ^ 7도 단순 연산이라면 가능성
	O(n log n) - 정렬 (N = 10만이면 1.66 x 10 ^ 6 수준, 매우 현실적)
	O(n ^2) - N = 1000이면 10 ^ 6, N = 10000이면 10 ^ 8 (이미 경계선)
		ㄴ> 내부 연산이 조금만 복잡해져도 위험함 (N = 100,000이면 10 ^ 10 거의 불가능)
	O(n ^ 3) - N = 500이면 1.25억 (Floyd-Warshall에서 O(V ^ 3)임)
	
	O(2 ^ n) - N < 20이라는 제한을 보면 subset 완전탐색이나 bitmask DP 의심
	O(n!) - 순열 전체 탐색에서 등장 (N = 10 정도까지는 완전탐색 문제라면 가능)
	
N < 20: 모든 부분집합, bitmask, backtracking, 2^n DP, meet-in-the-middle
N < 500: O(n ^ 2), 경우에 따라 O(n^3), 2D DP, pair comparison
N < 100,000: sorting, binary search, hash table, two pointers, prefix sum
N < 1,000,000: linear scan, prefix sum, frequency array, efficient hashing

	N = 20일 때,
		완전탐색 - 어떤 완전 탐색인지에 따라 다름
			부분 집합 전체라면 2 ^ 20 = 1,048, 576이므로 가능
			모든 순열이라면 20! = 2.43 x 10^18이므로 불가능
				ㄴ> 탐색 공간이 무엇인지 계산해야 됨
		정렬 - 당연히 가능 (20 log 20은 매우 작음)
		이중 반복문 - 가능 (20 ^ 2 = 400)
		DP 배열 - 당연히 가능 (vector<int> dp(n)라면 20칸 뿐)
	
	N = 100일 때,
		완전탐색 - 2 ^ 100 같은 exponential brute force는 불가능
		정렬 - 100 log 100 가능
		이중 반복문 - 100 ^ 2 = 10000 가능
		세중 반복문 - 100 ^ 3 = 1,000,000 가능
		DP 배열 - O(n)은 당연히 가능 (100 x 100짜리 2D DP도 매우 작음)
	
	N = 1000일 때,
		정렬 - 1000 log 1000 = 10,000 (가능)
		이중 반복문 - 1000^2 = 1,000,000 (가능)
		세중 반복문 - 1000^3 = 10^9 (대부분 불가능)
		DP 
			1차원 DP: O(n) (문제 없이 가능)
			2차원 DP: O(n^2) = 10^6 (메모리 타입 고려하면 충분히 가능)
	
	N = 100,000일 때,
		완전탐색 2^n - 불가능
		정렬 - 100,000 log 100,000 =1.7 x 10 ^ 6 (가능)
		이중 반복문 - 10 ^ 10 (불가능)
		1차원 DP - 100,000칸 (가능)
		2차원 DP - 100,000 ^ 2 = 10 ^ 10 (메모리부터 불가능)
	
	N = 1,000,000일 때,
		정렬 - 10^6 log 10^6 = 2 x 10^7 (정렬 자체라면 충분히 고려 가능)
		이중 반복문 - 10 ^ 12 (불가능)
		1차원 DP - 10^6칸은 대부분 가능
			C++ int가 일반적으로 4 byte면 10 ^ 6 x 4 = 4,000,000 bytes (4MB)
	

공간복잡도

	원소 개수는 10^10개, 4 byte int 기준 4 x 10^10 = 40 GB (메모리 제한 초과)

Two Sum
	배열 nums와 정수 target이 주어진다. 서로 다른 위치의 두 값을 더해 target을 만들기
		nums = [2, 7, 11, 15], target = 9 ==> true
	
		방법 1: 모든 쌍 확인 (O(n ^ 2))
			- 각 i에 대해 뒤쪽 원소들을 검사한다
			=> 실제 비교 횟수: n(n-1) / 2, => O(n ^ 2)
		
			N = 100,000이면, (100000 x 99999)/ 2 = 	5 x 10 ^ 9
			약 50억 개의 pair를 확인해야 됨 (= 사용하기 어려움)
			
			최적화 아이디어
				현재 숫자가 x라면 우리가 필요한 숫자는 x + y = target이므로
				y = target - x
					ㄴ> 현재 숫자를 볼 때마다 "이전에 target - x를 본 적이 있는가
					ㄴ> 이것을 빠르게 물어볼 수 있는 자료구조: Hash Set
				
			
		방법 2: Hash Set
			현재 값이 x라면 필요한 값은 target - x
				1) 이미 등장한 값들을 set에 저장해둔다
				2) 각 원소마다 target - x가 set에 존재하는가를 확인한다
			
			배열 한 번 순회: n개의 원소를 확인한다
			Hash Set의 평균적인 lookup, insertion: O(1)
				전체: n x O(1)이므로 O(n)
				ㄴ> 추가 공간은 최대 n개 값을 저장하므로 O(n)
			
		모든 쌍 검사: 시간 O(n^2), 공간 O(1)
		Hash Set: 시간 평균 O(n), 공간 O(n)
			더 빠른 알고리즘을 얻는 대신 메모리를 사용했음
			time-space trade-off 
		
		방법 3: 정렬 + Two Pointers
			1) 배열 정렬 ( [11, 2, 7, 15] ----> [2, 7, 11, 15])
			2) 양 끝에서 포인터를 시작 (L --- >2 7 11 15 <--- R)
			3) 합을 계산 (< target 이면 L++, > target이면 R--, 같으면 성공)
		
			정렬: O(n log n) / Two pointers: O(n)
				전체:  O(n log n) + O(n) = O(n)
			
	단순히 답이 나오는 코드를 작성한다
		=> 입력 제한을 만족하는 풀이 중 어떤 자료구조와 알고리즘이 가장 적절한가?
	
	중복 검사 - 배열 안에 중복된 값이 존재하는가?
		1) 모든 순서쌍 비교: O(n^2)
		2) Hash Set: O(n)
		3) 정렬: O(n log n) => 같은 값들끼리 이웃하므로 인접 원소만 비교
	

사고 패턴: 중첩 반복문을 보면
	ㄴ> 내부 반복문이 하는 작업을 더 빠른 자료구조로 대체 가능한가?
	
		모든 이전 값 탐색 => Hash Set Lookup (O(n) ---> O(1), O(n^2) ---> O(n))
	
	반복 탐색 O(n) ----> Hash Set / Hash Map O(1)
	정렬되지 않은 배열에서 반복 검색 O(n) ----> 정렬 + Binary Search O(log n)
	반복되는 구간 합 계산 O(n) ----> Prefix Sum 전처리 후 O(1)
	모든 pair 검사 O(n^2) ----> 정렬 + two pointers O (n log n)
	
	입력 제한 따라 같은 문제의 풀이가 달라짐
		Two Sum 문제
			N < 100이면 Brute Force 가능
			N < 10000이면 brute force로는 안 됨
				=> Hashing or Sorting 생각

	입력 제한을 볼 때 N 하나만 보지 마라
		N < 1000, Q < 100,000일 때 각 query마다 배열 전체를 탐색한다면
		O(NQ)이므로 최대값에서는 1000 x 100000 = 10^8
			입력이 여러 변수로 이루어진 경우에는 단순히 N만 보면 안 된다
		
		N < 100000, M < 200000 이라고 할 때
		그래프 전체를 한 번 순회하는 BFS/DFS는 O (N + M)이므로 약 300000 (현실적)
			adjacency matrix를 모두 검사한다면 O(N^2)이므로 10^10
			큰 sparse graph에서는 adjacency list가 자연스러움
	
	값의 범위도 확인
		1 < N < 100000, 0 < A[i] < 100 (원소 값의 범위가 매우 작음)
			hash map 대신 int freq[101] 같은 frequency array 사용
				(시간: O(n), 공간: O(101) = O(1))
		
		입력 제한에서 확인해야 할 것은 단순히 N만이 아님
			값의 범위, 그래프 정점/간선 수, 문자열 길이, 메모리/시간 제한
